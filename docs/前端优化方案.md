## 1. 现状问题诊断

> 以下诊断全部基于真实代码行号，按"信息架构 → 视觉呈现 → 交互体验 → 性能 → 可维护性"五类展开。严重度分级按 AGENTS.md §4.6（Blocker/Major/Minor/Note）。**本轮无 Blocker**——面板功能完整可用，问题集中在体验与效率层。

### 1.1 信息架构（IA）

**IA-1 总览页单屏信息过载，安全证据链被推到首屏之外 —— Major**

- 问题：总览面板（index.html L409-459）依次堆叠 10 个信息模块：4 张 KPI 卡（L410-422）→ 风险评分卡（L423-434）→ 攻击双通道趋势 + TOP 攻击源/端口（L435-449）→ 资源四图（L450-455）→ 事件摘要流（L456-458）。默认 24h 视图下，首屏只露出 KPI + 评分卡开头，"攻击趋势""TOP 攻击源"等核心安全证据链需滚动 1-2 屏。
- 影响：安全值班的核心诉求是"一眼判断当前有没有被攻击、攻击面是什么"。当前首屏 2/3 是计数卡片，攻击证据链（趋势/TOP）被压到下方；与用户"不直观"反馈直接对应。
- 严重度：Major

**IA-2 KPI 语义混杂，四个卡片不是同一信息层级 —— Minor**

- 问题：L411-421 四个 KPI 并列同一排："当前活跃连接"（WS 实时通道值，秒级）、"防火墙事件"（range 累计）、"SSH 失败"（range 累计）、"磁盘使用率"（实时水位）。连接/攻击/资源三个领域均权混排。
- 影响：视觉均权 = 无阅读顺序。攻击类计数（安全关注核心）与磁盘水位（运维关注）混排，扫读效率低。
- 严重度：Minor

**IA-3 同源数据多出口呈现：一条 drop 事件出现三处 —— Major**

- 问题：SSH 失败 / 防火墙 drop / 封禁三类事件同时出现在三组呈现中：① 总览事件摘要流（app.js renderEventStream L491-537，从 sshRows/fwRows/banRows 派生，最新 20 条）；② 攻击页三张明细表（renderSSH L601-619、renderFW L622-640、renderBans L643-659）；③ 总览迷你榜（L196-218）与攻击页 TOP 图（L545-598）。同一条防火墙 drop 在总览事件流与攻击页防火墙明细表中各出现一次。
- 影响：用户在不同页签看到"看似不同实则同源"的数据，产生冗杂感；事件摘要流（index.html L456-458，max-height 340px 固定）与攻击页明细表（检索/取证工具）用途不同（前者为时序叙事，后者为检索工具，AUD-FE-001 D-2），冗余应限定为"**同一信息层级重复呈现**"而非"模块无用"——正确处置是降级为"概览 → 明细"入口而非删除。
- 严重度：Major（直接对应"精简"诉求的核心病灶；处置方式见 3.3）

**IA-4 归档页信息容量过低 —— Minor**

- 问题：归档页仅一张 3 列表（月份/文件/大小 MB，index.html L499-503），数据变更频率约 1 行/月，却占据独立页签；磁盘水位告警语义（技术方案 §7 L957：warn ≥80% / critical ≥90% + 剩余可支撑天数）在面板中没有对应呈现位。
- 影响：页签平均信息价值被拉低；低频页签与高频页签并列，导航层无主次。
- 严重度：Minor

**IA-5 跨页签联动无状态可视化 —— Minor**

- 问题：攻击页 TOP 图点击发起的过滤（app.js L579-597）实际同时过滤连接事件查询（L770-772 connections 带 dst_port/src_ip 参数），但过滤状态 chip 只在攻击页顶部显示（index.html L469）。用户从攻击页发起端口过滤后切到连接页，看到的是被过滤后的连接数据，页面却无任何过滤指示。
- 影响：数据被静默收窄，用户可能误读"当前连接只有这些"；"直观"诉求受损。
- 严重度：Minor

### 1.2 视觉呈现（Visual）

**VI-1 顶部三层 chrome 纵向消耗过大，态势结论视觉权重不足 —— Major**

- 问题：页面顶部依次为 header（L80-110：标题 + 连接徽章 + 采样标注 + 时间范围，窄屏换行后可占 2-3 行，L379-384）→ nav（L293-309）→ 态势条（L217-228）。三条 chrome 在 720px 以下视口可占首屏 25%+。同时，态势条作为最重要的安全结论，字号仅 13px（L219）、折叠后 12px（L228），视觉权重与其信息价值不匹配。
- 影响：数据区首屏占比被压缩；"当前安全态势"这一最该突出的结论反而不突出。
- 严重度：Major

**VI-2 KPI 字号层级断层 —— Minor**

- 问题：KPI 数字 28px/600（L191）、标签 12px（L354）、note 11px（L214）——12 → 28 之间无中间档；卡片标题 h3 12px（L330）。note 承载口径说明（"实时值（无历史序列）""含 drop/accept"），11px 可读性差。
- 影响：层级跳跃造成"只有大数字"的观感；口径说明（安全语义重要）视觉上被弱化到接近不可读。
- 严重度：Minor

**VI-3 零攻击庆祝态遮挡真实空数据 —— Minor**

- 问题：全零时绿色徽章 rgba(17,22,29,0.78) 半透明遮罩覆盖整个图表区（zero-badge，L241-247），完全挡住坐标轴/网格；文案"✓ 无攻击记录"（L441）为情绪化表达。
- 影响：监控面板中"空视图"本身就是信息（真实空 vs 未加载），遮罩使其不可验证；与"数据完整性"直觉相悖。
- 严重度：Minor

**VI-4 事件流视觉区分度低 —— Note**

- 问题：三类事件（SSH 失败/fw drop/封禁）仅靠 7px 圆点颜色区分（L262-264），文本统一 12px 灰（L266）；分组标题 11px 微弱色（L253）。
- 影响：滚动扫视时难以快速定位"封禁"等高价值事件。
- 严重度：Note

**VI-5 图表色板内部饱和落差 —— Note**

- 问题：CSS 侧为低饱和体系（--accent #4C9AFF、语义三色均低饱和，L18-54），而 ECharts 色板 TI.chart（app.js L48）含 #ff5286（粉红）、#b877d9（紫）、#6ed0e0（青）三个高饱和色，且 6 色中仅 3 色在 UI 实际使用（accent 蓝/橙/绿）。
- 影响：图表与 UI 两套色感并置，体系内部一致性弱；违反 design-taste 单强调色纪律（§4.2）。
- 严重度：Note

### 1.3 交互体验（Interaction）

**IN-1 联动过滤单向、入口单一，明细表无反查能力 —— Major**

- 问题：过滤只能由攻击页 TOP 图柱条点击（app.js L581-596）或总览迷你榜点击（L208-210）发起；SSH 明细表、防火墙明细表等 6 张表格的行均不可点击过滤。过滤 chip 仅攻击页可见（index.html L469）。
- 影响：分析路径"看到可疑 IP → 查该 IP 全部行为"需要先复制 IP，再无法直接输入（无过滤输入框），只能绕回 TOP 图点击——操作路径断裂，对应"不直观"反馈。
- 严重度：Major

**IN-2 30d 视图攻击数据降频无提示 —— Minor**

- 问题：30d 范围攻击类轮询降频至 30s（app.js L851 minGap=30000），UI 无任何说明。
- 影响：用户看到 TOP 图/明细"不动了"会误判为数据停滞，损害实时性信任。
- 严重度：Minor

**IN-3 无数据新鲜度指示 —— Minor**

- 问题：全页面无"最后更新于 xx:xx"时间戳；WS 断开降级轮询时（L929-934），用户在徽章变红前无法感知数据源状态。
- 影响：监控场景的基础信任要素缺失。
- 严重度：Minor

**IN-4 WS 状态被 system 帧覆盖 —— Note**

- 问题：system 帧直接把徽章文字替换为"WS 实时 · source: message"（L925-927），持续推送时连接状态（ok/degraded/error 三级，L30-35）语义被掩盖。
- 影响：状态语义退化，用户无法区分"WS 实时"与"WS 实时 + 系统消息"。
- 严重度：Note

**IN-5 页签切换无过渡、隐藏面板图表持续渲染 —— Minor**

- 问题：switchPanel（L944-951）直接 display 切换无过渡；切页时对全部图表 resize（L950），但隐藏面板的图表每轮轮询仍被 setOption 重绘（见 PF-2）。
- 影响：切换生硬（"不够现代化"的直接体感来源之一）；隐藏页白耗 CPU。
- 严重度：Minor

**IN-6 可访问性基线弱 —— Minor**

- 问题：态势条为 div+click 实现（index.html L405-407、app.js L962-968），无键盘可达性；表格无 caption/scope；排序指示仅字符箭头（L186-188）；图表无 aria 降级文本。focus-visible 已部分覆盖（L131/143/180/309）。
- 影响：键盘/读屏用户基本不可用。
- 严重度：Minor

### 1.4 性能（Performance，1C1G 红线）

**PF-1 轮询无差别全量拉取，低变更数据 5s 一查 —— Major**

- 问题：pollOverview（L727-782）每 5s 固定拉取 5 类数据：summary、resources(1h)、snapshot、connections、archive。其中 archive 月级变更（L698-712 仅月份/文件/大小）、snapshot 由 20s 级采集器支撑（index.html L461 注"ss 快照 20s 采集"）——二者变更频率远低于轮询周期，在非归属页签激活时属无效拉取；connections 服务于连接页表格（renderConns 的唯一数据源，L773-776），在总览页无呈现位——**正确处置是"按呈现位归属挂轮询"（连接页激活才拉，见 7.4），而非简单移出**（AUD-FE-001 D-3 口径）。
- 影响：1C1G 上每 5s 约 5-6 个 HTTP 请求；低变更数据重复查询浪费带宽与 SQLite 查询（技术方案 4.6：查询按范围扫描，archive 表虽小但属无谓 I/O）。
- 严重度：Major

**PF-2 ECharts 全量重绘（notMerge）+ 隐藏面板照常渲染 —— Major**

- 问题：所有图表 setOption 均为 notMerge=true（L99-107、L558-576），5s 一轮全量重建；且面板 display:none 时对应图表仍在轮询渲染（renderResource/renderAttacks 无可见性判断）。
- 影响：ECharts 5.5.1 本地 1.03MB（V4 报告 L25/18 行证据）在 1C1G 上的 diff/重绘开销被无谓放大；连接/归档页激活时总览图表照样每 5s 全量重绘。
- 严重度：Major

**PF-3 表格与事件流全量 innerHTML 重建 —— Major**

- 问题：6 张明细表每轮 tbody.innerHTML='' 后逐行 createElement（如 renderFW L630-639，最多 200 行）；事件流同样全量重建（L514 box.innerHTML=''）。
- 影响：每 5s 数千 DOM 节点创建/销毁，主线程抖动；1C1G 上 INP 恶化风险。
- 严重度：Major

**PF-4 事件流固定 340px 高 —— Note**

- 问题：.event-stream max-height 340px（L251），1h/24h 视图 20 条分组内容通常不满；总览页被"又一张固定高卡"占用。
- 影响：总览滚动长度增加。与 IA-3 同源（收敛后自然缓解）。
- 严重度：Note

### 1.5 可维护性（Maintainability）

**MA-1 app.js 单文件 1006 行，职责混杂 —— Major**

- 问题：数据拉取（pollOverview/pollAttack/applyFilter）、渲染（17 个 renderXxx）、交互（bindSort/switchPanel）、状态（state 单例 L10-27）全部在一个 IIFE 内；文件注释散布 9 个 DEV 迭代编号（L1-4 头部含 DEV-015/014，DEV-012~DEV-020 分散各处）；connections 查询逻辑在 pollOverview（L770-776）与 applyFilter（L877-881）重复实现两遍，存在口径漂移风险（AUD-FE-001 MA-01）。
- 影响：任何一次设计迭代（含本方案落地）都需在 1006 行内定位修改，回归风险高。
- 严重度：Major

**MA-2 index.html 内联样式散落 —— Minor**

- 问题：grid-column span 2、margin-bottom:12px、height:220px 等硬编码内联 style（L423/435/436/456/471-473 等）；CSS 385 行全内联于 <style>（L8-385）。
- 影响：样式与结构耦合，组件级统一调整成本高。
- 严重度：Minor

**MA-3 魔法数字与常量散落 —— Note**

- 问题：POLL_MS=5000（L8）、RANGE_SEC（L716）、30d 节流 30000（L851）、limit 参数 10/200/500（L788-826）分布在代码各处。
- 影响：调参/审计困难。
- 严重度：Note

## 2. 设计目标与原则

### 2.1 用户三诉求 → 设计原则映射

| 用户诉求 | 落地原则 | 对应诊断 | 主要手段 |
| :--- | :--- | :--- | :--- |
| **现代化**（视觉与交互） | ① 视觉系统一致性锁：单一强调色 + 语义三色资产不变；字号/间距/圆角全尺度化；② 交互反馈完备：hover/active/focus/状态指示全覆盖；③ 数据即主角：chrome 让位，图表与大数字承担视觉层级 | VI-1/VI-2/VI-5/IN-5 | 态势条权重升级；KPI 层级补档；图表色板收敛；页签过渡 |
| **直观**（信息呈现与操作路径） | ④ 结论先行：安全结论（态势条/评分）置于首屏最上；⑤ 证据链闭环：评分→趋势→TOP→明细的阅读路径单向展开；⑥ 反查可达：任意数据点（表格行/迷你榜）可发起联动过滤 | IA-1/IA-2/IN-1/IA-5 | 首屏重组；表格行点击过滤；过滤状态全局化 |
| **精简**（去冗杂） | ⑦ 一数一出口：同源数据只保留一个主出口，其余降级为入口/折叠；⑧ 折叠隐藏：低频/明细模块默认折叠，按需展开；⑨ 刷新分级：数据按变更频率分档刷新，低变更数据不打扰 | IA-3/IA-4/PF-1/PF-2/PF-3 | 事件流收敛；资源区折叠；archive/snapshot 降频 |

### 2.2 继承的既有纪律（不推翻，只在缺口上补充）

### 3.2 总览页首屏重组（IA-1 修复）

现状：`KPI×4 → 评分 → 趋势+TOP → 资源×4 → 事件流`（L410-458）。

优化目标布局（详见第 5 章线框图）：

```
L0 态势条（升级为"态势头"，权重提升）          ← 结论
L1 风险评分（左侧环形仪表）+ 攻击双通道趋势（右侧大图）   ← 决策证据
L2 4 张 KPI（2×2 分组：攻击组 / 系统组）        ← 关键计数
L3 TOP 攻击源 + TOP 被攻击端口（迷你榜，保留点击联动）
L4 系统资源（CPU/内存/磁盘/网络四图，默认折叠为一条）
L5 最近事件摘要（默认折叠，展开见最近 20 条）
```

- **评分与趋势同排**：环形仪表（L426 现有 200×150px）与双通道趋势图（L438 现有 220px 高）并列首屏，替代"评分独占一行 + 趋势独占一行"的两行布局，首屏可见决策模块从 2 个（KPI、评分）增至 4 个（评分、趋势、TOP 榜、态势头），首屏信息密度提升约 40%（估算：原首屏约 1.5 屏内容压缩至 1 屏，具体数值以 P0 实施后浏览器实测为准）。
- **KPI 语义分组**：L411-421 四卡改为 2×2（攻击组：防火墙事件 / SSH 失败；系统组：活跃连接 / 磁盘使用率），组间用间距分隔，组内并排。KPI 数值/trend/spark/note 结构（L190-214）不变。
- **资源四图默认折叠**：L450-455 四图收进"系统资源"可展开区（一行头 + 展开按钮），展开后为现有 2×2 网格。功能保留，默认隐藏。
- **事件流默认折叠**：L456-458 收进"最近事件"可展开区，默认只显示 3 条 + "展开全部"；展开后与现状一致（最新 20 条，10 分钟分组）。

**与硬约束的核验**：KPI 卡、风险评分环形仪表、攻击双通道趋势、TOP 攻击源/端口、时间范围切换全部在首屏或次屏原样保留；资源四图与事件流为"折叠隐藏"而非删除。

### 3.3 一数一出口：事件流与明细表去重复（IA-3 修复）

- **原则**：总览"最近事件摘要"定位为**实时性窗口**（看"正在发生什么"），攻击页明细表定位为**分析工具**（排序/过滤/联动）。两者关系从"重复"改为"概览 → 明细"。
- 具体手段：
  1. 总览事件流条目增加"跳转到攻击页对应表"操作（点击条目 → 切页 + 预置过滤，复用现有 applyFilter 机制 L868-882）；
  2. 事件流默认折叠为 3 条（见 3.2），避免与明细表视觉重复；
  3. 三类事件的视觉区分从 7px 圆点（L262-264）升级为"圆点 + 左侧 2px 语义色条 + 关键字段高亮"（SSH 失败显示用户名、fw drop 显示 源IP→端口、封禁显示 IP+Jail），扫视可定位。
- 保留理由：事件流是总览页唯一实时更新的"活动感"来源（WS 新条目高亮 L269-275 已有），直接删除会伤实时感知——收敛 + 降级为入口是正确取舍。

### 3.4 归档页增值（IA-4 修复）

- 保持单表（月份/文件/大小，L501），但卡片头改为"归档副本 + 磁盘水位"：在表上方加一行磁盘水位条（数据复用 summary.disk_percent 与 resources 24h 序列，app.js L756-762 已有拉取），显示"当前水位 62.3% · 剩余约 N 天"（N 由近 30 天增量速率线性外推，技术方案 §7 L957 已有语义）。
- 功能核验：表内容不变，仅加信息头；磁盘水位数据源已存在，零新 API。

### 3.5 过滤状态全局化（IA-5 / IN-1 修复）

- **filter chip 从攻击页移至全局**：现有 #filter-chip（L134-143、L469）移到 header 区（与时间范围同行或下方），任何页签可见；chip 文案带"来源"（"过滤：端口 :22 ✕（来自攻击页）"）。

### 9.3 兼容性风险

- **浏览器基线**：现有代码已用 `:has()`（L201）、`prefers-reduced-motion`、`fetch`/`WebSocket`/`clipboard`——本方案不抬升基线；新增使用 `details/summary`（现代浏览器全支持）与 `aria-sort`，无兼容回退需求。
- **旧测试依赖**：tester DOM 断言依赖元素 id（TEST-004 FE-2 口径）；本方案**保留全部既有 id**（chart-*、*-table、top-*-mini、conn-status 等），仅新增 id/class；折叠区为新增包裹层，不影响既有断言。
- **归档表等低频查询**：P0 将 archive 改为页签激活拉取后，测试若在总览页断言 archive 数据将失败——需在交付说明中标注该行为变化（行为变化清单见 10.3）。

### 9.4 与"精简"诉求的张力（须记录）

- 事件流折叠后，总览页"活动感"下降——缓解：折叠头实时显示最近 1 条事件摘要（"最近：203.0.113.5 SSH 失败 @ root"），活动感保留且不占高度。
- KPI 2×2 分组后，首屏计数可见性不变但顺序变化——缓解：攻击组靠左（阅读起点），符合安全优先。
- 折叠区默认折叠可能让新用户找不到资源图——缓解：折叠头文案显式（"系统资源（CPU/内存/磁盘/网络）"），且折叠区初始状态 = 展开（仅用户手动折叠后记忆该状态，sessionStorage 可存，低成本）。
