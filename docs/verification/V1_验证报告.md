## 2. 步骤 1：宿主裸测

### 2.1 环境

- 内核：6.18.33.2-microsoft-standard-WSL2，nf_conntrack 模块已加载（/proc/net/nf_conntrack 存在）
- 工具：iptables v1.8.7（nf_tables 后端）、conntrack v1.4.6、hping3
- 主网卡：eth4（<LAN_IP>）

### 2.2 轮 A（本机 IP 发包，local delivery 路径）

操作序列（`v1_host_test.sh`）：

1. 插入最小 drop 规则：`iptables -I INPUT -p tcp --dport 9999 -j DROP`，回读确认 `-A INPUT -p tcp -m tcp --dport 9999 -j DROP`
2. 后台 `conntrack -E -p tcp` 监听
3. hping3 向本机 <LAN_IP>:9999 发 5 个 SYN（目标端口未监听）

conntrack -E 输出（原文节选）：

```
    [NEW] tcp      6 120 SYN_SENT src=<LAN_IP> dst=<LAN_IP> sport=1202 dport=9999 [UNREPLIED] src=<LAN_IP> dst=<LAN_IP> sport=9999 dport=1202
    [NEW] tcp      6 120 SYN_SENT src=<LAN_IP> dst=<LAN_IP> sport=1203 dport=9999 [UNREPLIED] ...
    [NEW] tcp      6 120 SYN_SENT src=<LAN_IP> dst=<LAN_IP> sport=1206 dport=9999 [UNREPLIED] ...
conntrack v1.4.6 (conntrack-tools): 5 flow events have been shown.
```

conntrack 表检查（DROP 之后）：

```
ipv4     2 tcp      6 113 SYN_SENT src=<LAN_IP> dst=<LAN_IP> sport=1204 dport=9999 [UNREPLIED] ... mark=0 use=1
ipv4     2 tcp      6 113 SYN_SENT src=<LAN_IP> dst=<LAN_IP> sport=1205 dport=9999 [UNREPLIED] ... mark=0 use=1
```

**轮 A 结论**：5/5 SYN 产生 NEW 事件；DROP 后连接条目在表中保留（UNREPLIED，等待超时回收）。证明 conntrack 建表先于 INPUT drop 规则，被丢弃的包同样被全量记录。

### 2.3 轮 B（ip netns 外部源，veth 路径）

- 拓扑：netns v1test（10.99.0.2）→ veth0（主 netns 10.99.0.1）→ INPUT drop 9999
- tcpdump 确认 3 个 SYN 到达主 netns veth0；iptables 计数器确认 DROP 规则命中 3/3
- **主 netns 与 netns 内均无 conntrack 事件/条目**（对照：主 netns 内部向 10.99.0.1 发包正常建表）

**轮 B 差异记录**：WSL2（microsoft-standard 内核）中跨 netns（veth 对）进入主 netns 的包不产生主 netns conntrack 事件，属于 WSL2 定制内核行为（推断：veth 路径被内核特殊处理，与微软定制网络栈相关），非标准 Linux 行为。**验证手段缺陷不影响步骤 1 结论**（轮 A 已给出决定性证据）；VPS 实机复验时从真实外部源重复本场景确认。

### 2.4 步骤 1 结论

**通过**。被 DROP 的包产生 conntrack NEW 事件（轮 A 证据），"防火墙日志采样 + conntrack 全量"双通道互补论证成立。

## 3. 步骤 2：容器复测（V1b-1）

### 3.1 容器环境说明

- WSL Ubuntu 内 **docker 不可用**（Docker Desktop WSL 集成未启用；docker-desktop 发行版拒绝直连），按任务书语义评估后：
  - 无法在目标形态（WSL 内容器）复测 → 需在报告中标记 BLOCKED 项
  - 但 Windows 侧 Docker Desktop 可用，其 Linux 容器（--network host）运行于 Docker Desktop VM——**该形态与目标 VPS 容器形态有差异**（VM 而非宿主），故本报告将其作为"部分复测"，VPS 容器复验仍列入 M4 前清单
- 容器：alpine:3.20，`--network host --cap-add NET_ADMIN`

### 3.2 结果

1. **容器内 conntrack -E 可见 host netns 全部事件**（观察到 VM 内 docker 服务 2376 端口大量 NEW/UPDATE/DESTROY 事件）→ 验证"host 网络模式下容器可订阅宿主 conntrack 事件流"
2. **DROP 复测**：容器内 `iptables -I INPUT -p tcp --dport 9999 -j DROP` + nc 5 次连接尝试 → 5 条 `[NEW] tcp SYN_SENT ... dport=9999` 事件 + 表中 UNREPLIED 条目 → 与步骤 1 轮 A 结论一致
3. iptables 规则成功插入/清理/回读（INPUT 链恢复 ACCEPT 原状）

### 3.3 步骤 2 结论

**通过（Docker Desktop VM 形态）**。容器形态下 DROP 事件行为与裸机一致。**注意**：WSL 内 Docker 不可用的事实已记录；V1b-1 的最终确认（root 免 cap 行为、VPS 容器形态）列入 M4 前 VPS 复验清单。
