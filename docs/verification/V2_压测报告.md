### 2.3 netlink 溢出行为（R-10，退出标准核心）

| 项 | 实测 |
| :--- | :--- |
| 溢出发生 | 是：压测开始后 ~2 分钟（峰值事件率期间），`netlink receive: recvmsg: no buffer space available` |

| 自动恢复 | system_event（level=warn）"conntrack 监听异常终止，2s 后自动重启（R-10 恢复路径）"；重启后事件流恢复 ✅ |
| 溢出期间丢事件 | 有（netlink 内核侧丢弃，留痕可查）——符合方案"唯一可能丢失点是内核侧 netlink 溢出（R-10，须留痕）" |
| overrun 通道（/proc Drops 计数） | 未触发（0 事件）：WSL2 下 /proc/net/netlink 的 Drops 列未随溢出更新（推断为 WSL2 内核行为，errChan 留痕路径已独立验证生效）；**VPS 复验时复核该计数路径** |

### 2.4 稳态事件率分析

SYN flood 持续发包但稳态事件率降至 ~0.6/s，同时 conntrack -S 显示 insert_failed=0、early_drop=0（表未满）。推断：WSL2 环境下 hping3 raw socket 发送速率受内核/调度限制（hping3 CPU 自峰值 110% 降至 ~1%），非采集端瓶颈。采集端在 9,800/s 峰值下稳定工作（峰值已超过方案 4.5 DDoS 估算上界 500–1,000/s 近 10 倍），鲁棒性验证充分。

## 3. 压测中发现问题与修复（Blocker）

**问题**：netlink 缓冲溢出（ENOBUFS）后 go-conntrack 库终止 receive 循环，连接事件流静默中断（首轮实测 96s 无新事件），违反"无静默丢事件"退出标准。

**修复**（提交 `cd49fc9`）：
1. 监听终止检测 + 自动重启（退避 2s→30s）
2. 重启伴随缓冲扩容（上限 8MB）
3. 启动时提升 net.core.rmem_max 至 8MB（默认 212992 会截断 2MB 配置）

**复测**：修复版压测 30 分钟，溢出 1 次 → 留痕 → 2s 自动恢复 → 事件流连续。修复有效。

## 4. 结论

V2 压测**通过**：
- 30 分钟无崩溃、无静默丢事件（除溢出留痕）✅
- 资源预算对照：CPU 达标（稳态 0.2–0.7%），RSS 9.9–10.4MB 低于预算下界 ✅（对照 5.1 无需回写超差项）
- R-10 溢出留痕 + 自动恢复路径实测验证 ✅
- 遗留：overrun 通道的 /proc Drops 计数在 WSL2 未观测到（留痕双通道之一），VPS 复验时复核
