## 已复现的原因与证据边界

1. 旧前端每 5 秒发起查询，未对相同请求去重；筛选变化仅丢弃旧响应，不取消旧工作。本次增加同序列、同 URL 去重、取消与有限并发。
2. 旧 `aggTimeout` 将 7 天范围分到 5 秒短档，反而短于 24 小时。原镜像在 16 MB 和 128 MB 临时空间下，7 天四个聚合接口都在约 5 秒返回 500，日志为 `context deadline exceeded`。
3. 16 MB `/tmp` 无法承载长窗口排序：30 天趋势请求返回 500，耗时 28.506 秒，日志为 `database or disk is full (13)`。观察到查询中 `/tmp` 已使用 10,000 KB，查询结束后的空闲容量不能代表峰值。
4. 仅将测试容器 `/tmp` 扩到 128 MB，仍有 30 天查询在 15～30 秒超时，不能把扩容当成完整修复。
5. 原时间索引不含聚合列，查询需要反复回表；候选增加 `idx_fw_ts_stats(ts, action, dst_port, src_ip)`。执行计划确认使用覆盖索引。覆盖索引避免回表、分组排序可能使用临时 B-tree 的机制见 [SQLite 查询计划文档](https://www.sqlite.org/queryplanner.html)与[临时文件文档](https://www.sqlite.org/tempfiles.html)。本项目改进效果以实际对照数据为准。
6. 覆盖索引与 128 MB 临时空间配合后，单路、双路查询成功；四路并发仍可发生空间不足。因此增加共享双执行槽，在取得数据库连接前拒绝超额聚合请求，而非继续排队至 500。

不能从这些结果推断所有历史 500 都已逐条找到原因；本次验收只覆盖下述明确接口、负载和浏览器行为。两路聚合限制针对 summary、top_ports、top_sources、firewall/timeline，不代表所有导出及其他 API 的全局并发上限。

## 实际改动

- 前端：两路请求并发、相同请求仅保留最新回调、35 秒含响应解析超时、切换时取消旧请求、忽略陈旧响应、429 按 `Retry-After` 全局退避。
- 长范围：7 天、30 天攻击统计每 30 秒轮询；资源监控仍每 5 秒刷新，主动切换立即请求，页面提示同步更新。
- 数据库：仅新增覆盖索引，保留旧索引、表结构和记录；按原时间范围、小时对齐与四通道语义聚合。
- 后端：修正 7 天与默认窗口超时档，30 天上限 30 秒；完整检查统计查询 Scan 和迭代错误，防止把部分结果作为成功数据。
- 过载：指定四路聚合共用两个执行槽；超额立即返回 429 与 `Retry-After: 2`，保持既有速率令牌桶，不放宽访问限制。
- 部署：`/tmp` 上限从 16 MB 调整到 128 MB，按需占用并计入原 512 MB 容器限额；CPU 1.6、非 root、host 网络、capabilities、挂载与采集配置保持不变。

### 回滚与边界

备份和本次完整清单在 `/opt/sentry-backups/20260909-perf`，原镜像及源码保留。紧急镜像回滚可使用已校验的完整清单，不恢复旧数据库快照：

```sh
docker compose -p deploy --project-directory /opt/vps-safe-dashboard/deploy \
  -f /opt/sentry-backups/20260909-perf/rollback.compose.json \
  up -d --no-build --pull never --no-deps sentry-agent
docker image tag sha256:5201f02d13bd199692d7cfbbd37df41b32f687e62a84d117e34d6e35dcf5c806 sentry-agent:latest
```

此人工入口恢复旧镜像及清单中的 16 MiB 临时空间；原 Compose 文件仍保留本次 128 MiB 设置，后续常规重建会使用该值。若需要精确恢复原文件，须在核对当前哈希后以原子替换方式恢复备份，不能直接截断写入。发布器自身失败路径会自动处理此恢复。不要再次直接运行已归档发布器的 apply：它只适用于精确旧镜像／旧 Compose 基线，成功发布后前置校验应拒绝继续。

残余风险：备份并行时曾出现一次 30d 超时，根因未严格确证；避免将大库校验与长范围压测安排在同一时段。`-race` 仍未完成；两路执行槽不涵盖所有导出 API；本次没有承诺持续监控、所有负载均无超时或新增大版本功能。
