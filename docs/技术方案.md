## 1. 设计目标与约束

### 1.1 需求基线（已由用户确认，不可更改）

1. **全量连接与日志记录**：资源使用率（CPU/内存/磁盘/网络）、TCP/UDP 连接、SSH 登录尝试、防火墙日志全部记录，不做预过滤，宁可多记不可漏记。
2. **攻击识别靠聚合现有防护日志**：解析 fail2ban、iptables/nftables、SSH 认证日志统计攻击态势，不引入重型检测引擎。
3. **Web 仪表盘展示**：数据留在 VPS 本地存储，通过 Web 实时查看。
4. **最高优先级约束：轻量化、不耗资源**。按低配 1C1G VPS 假设，采集端常驻 CPU < 1%~2%、内存 < 100MB 为设计目标。
5. VPS 具体发行版/内核版本未知，方案必须包含"部署前环境检查清单"与分支处理逻辑。

### 1.2 硬约束

| 项 | 约束值 | 说明 |
| :--- | :--- | :--- |
| 硬件假设 | 1 核 / 1GB 内存 VPS | 最低配基线，方案按此设计 |
| 采集端常驻 CPU | < 1%~2% | 全栈（含 fail2ban）典型值可能触及上界，见第 5 章 |
| 采集端常驻内存 | < 100MB | 不含外部组件；全栈口径见第 5 章 |
| 单机部署 | 无多机集中管理 | 仅预留扩展接口（第 13 章） |
| 数据本地化 | 数据不出 VPS | 面板访问方式由用户自配（参考建议见 6.7） |

### 1.3 设计原则

| 编号 | 原则 | 落地含义 |
| :--- | :--- | :--- |
| P1 | 只记录不预判 | 所有数据源全量采集入库；过滤仅在展示层（面板查询参数）进行，采集路径不做业务级丢弃 |
| P2 | 聚合现有防护日志 | 攻击态势 = fail2ban + 防火墙日志（iptables/nftables）+ SSH 认证日志的聚合统计，不引入重型检测引擎（含不引入 crowdsec，见 R-04） |
| P3 | 事件驱动优先于轮询 | 连接、日志变化用事件流（conntrack netlink、journald/rsyslog 流式）采集；仅资源指标（/proc）用 5s 轮询 |
| P4 | 单进程单二进制 | Go 单二进制后端内嵌全部采集与 Web 能力，无独立采集进程、无 Python 运行时 |
| P5 | 采样必须显式标注 | 防火墙日志限速、ss 快照等采样性质通道在面板与文档中显著标注，不伪装成全量 |

## 2. 系统架构

### 2.1 架构总览

单进程 Go 二进制（`sentry-agent`，暂定名），最终交付为 Docker 镜像，运行于宿主机 Docker 运行时之上（`--network host` 共享网络命名空间，见 6.4）；内部以协程组织各采集通道，统一写入 SQLite（卷挂载持久化），同时对外提供 HTTP API 与 WebSocket 实时推送。外部组件仅限系统既有服务（journald/rsyslog、fail2ban、nftables/iptables），均位于宿主机，容器以只读挂载方式访问其数据；面板访问方式由用户自配（工具仅暴露监听端口）。

### 2.2 数据流

**2.2.1 常态数据流（各通道独立，互不阻塞）**

1. 资源：M-01 每 5s 读一次 /proc（CPU 差值、内存、磁盘、网络计数差值），产出 `ResourceSample`。
2. 连接：M-02 双通道——①conntrack 事件监听（NEW/UPDATE/DESTROY，内核按事件推送，事件率与连接速率成正比）；②ss 快照协程每 20s 执行一次 `ss -tanup` 解析，产出当前连接列表（仅展示用途，见 2.4 第 1 条）。
3. SSH：M-03 通过纯 Go journal 解析器流式读取挂载的宿主 journal 目录（SSH 认证条目），或回退 `tail -F /var/log/auth.log`（rsyslog 分支），按行解析认证结果。
4. 防火墙：M-04 同通道过滤内核条目（`_TRANSPORT=kernel`），解析 nft/iptables LOG 行，按规则前缀过滤。
5. fail2ban：M-05 流式读取 /var/log/fail2ban.log（Ban/Unban/Found），产出 `BanEvent`；每 60s 只读查询 fail2ban.sqlite3 刷新当前封禁名单（D-02 决策后按选择启停）。
6. 统一入队：各通道产出的标准化事件进入各自有界 channel（容量 4096，背压策略见 2.3.3）。
7. 落库：M-06 单写线程消费各 channel，每 1s（或积满 500 行）批量事务写入 SQLite WAL。
8. 展示：M-07 提供 REST 查询与 WS 推送；前端 M-08 按 5s 刷新资源图、按 1s 聚合推送连接/攻击事件。

**2.2.2 攻击场景数据流（洪泛保护路径）**

- 连接通道：攻击连接同样产生 conntrack 事件（推断，见 V1 验证项），事件率可能上升至每秒数百；写路径自动合并为批量事务，超过单批容量则拆批，进程内不丢事件（背压传导链见 2.3.3）；netlink 缓冲溢出时记录 `system_events`（R-10）。
- 防火墙通道：内核侧限速（默认 5 包/s 突发 10）保证该通道事件率有上界；超限部分被内核丢弃（采样性质，面板标注，R-09 首要缓解）。
- SSH 通道：journald RateLimit 调高（R-11）或走 rsyslog，保证暴力破解阶段不丢行。
- 磁盘：水位监控（R-09 最高优先级，D-04 永久保留后无自动回收）在阈值触发时写 `system_events` 并保留采集（不主动停采），压缩副本生成在低峰执行、critical 时暂停。

**2.2.3 展示查询数据流**

- 短查询走 SQLite 索引（按 ts/dst_port/src_ip），全部只读连接，与写线程隔离（WAL 允许读写并发）。
- WS 推送由 M-07 从各采集 channel 复制订阅（非阻塞、可丢弃陈旧快照），不重复查库。

### 2.3 进程与并发模型

**2.3.1 单进程理由**

- Go 单二进制静态编译，无解释器运行时；实测基准常驻 10–50MB（SEA-001），是唯一确定落在 100MB 预算内的选项。Python FastAPI 备选方案约 100–150MB，有超标风险（R-01），仅作备选（第 10 章决策项 D-01）。

**2.3.2 协程划分**

| 协程 | 职责 | 数量 | 退出条件 |
| :--- | :--- | :--- | :--- |
| resourceCollector | /proc 轮询 | 1 | ctx 取消 |
| conntrackListener | netlink 事件读取 | 1 | ctx 取消 |
| connSnapshotter | ss 快照（当前连接列表，仅展示） | 1 | ctx 取消 |
| sshParser | journald/rsyslog 流解析 | 1 | ctx 取消 |
| fwParser | 内核日志流解析 | 1 | ctx 取消 |
| f2bListener | fail2ban 日志流解析 + 封禁名单刷新 | 1 | ctx 取消（D-02 停用时置位退出） |
| dbWriter | 单写线程，批量事务 + 归档执行 | 1 | 队列排空 + ctx 取消 |
| httpServer | HTTP + WS | 1 | 监听关闭 |
| archiver | 定时触发归档任务（投递给 dbWriter 执行） | 1 | 定时触发（每日 02:00 检查，每月 1 日执行归档） |
| diskMonitor | 磁盘水位检查 | 1 | 每 5 分钟 |

**2.3.3 队列与背压（传导链显式化）**

- 每个采集通道使用有界 channel（默认容量 4096）。
- 消费侧（dbWriter）是唯一慢路径：写满时 dbWriter 保持单批最大耗时（目标 <50ms/批，见 M2 验证 V3）。
- **背压传导链（必须理解，防误读"不丢事件"）**：channel 满 → 对应采集协程阻塞在发送 → 该协程停止读取数据源。对 conntrack（内核推送模式）而言，停读 netlink 会导致**内核缓冲溢出**，溢出事件在内核侧被丢弃（R-10 监测留痕）；对日志流（journald/rsyslog 文件流）而言，停读不会丢数据（内核/文件缓冲无界，恢复后继续消费，仅延迟）。因此"不丢事件"的确切语义是：**进程内不主动丢弃任何已读到的数据**；唯一可能丢失点是内核侧 netlink 溢出（R-10，须留痕）与防火墙内核限速（采样性质）。DDoS 场景下写路径若持续满载，缓解手段是扩大 batch 容量与调大 netlink 缓冲（上限 8MB），而非丢数据。

### 2.4 关键设计取舍说明

1. **conntrack 事件驱动 vs ss 轮询**：全量记录以 conntrack 为主通道；ss 快照仅用于面板"当前连接列表"展示（10–30s 间隔），快照漏短连接由 conntrack 全量记录补偿——不影响"只记录"目标。
2. **被 DROP 的连接**：netfilter 钩子顺序下，被 DROP 的攻击连接仍产生 conntrack NEW 事件（推断，依据 netfilter 优先级 conntrack 先于 drop 规则，但尚未实测）；此推断是"防火墙日志采样 + conntrack 全量"双通道互补的关键假设，列为 V1 验证项，M1 开工首日验证，失败则调整（影响面见 11.1 与风险表 R-02 论证链）。
3. **防火墙日志采样性质**：限速后的防火墙日志是"被攻击端口"统计的采样视图，面板显著标注；完整视图由 conntrack 通道（含 DROP 连接事件，经 V1 验证后）补齐。
4. **无独立采集进程**：采集逻辑全部并入 sentry-agent 进程，避免多进程内存叠加。

## 3. 模块划分与职责

> 模块接口以 Go 伪代码给出，M2/M3 实施时按此签名实现，不做架构级再决策。所有时间戳统一为 Unix 秒（int64）。IP 存储：IPv4 统一存无符号 32 位整数（INTEGER），API 层负责二进制与点分十进制的互转（见 4.2 说明）；IPv6 存 TEXT。

### 3.1 M-01 资源采集模块

| 项 | 定义 |
| :--- | :--- |
| 职责 | 每 5s 采集 CPU/内存/磁盘/网络计数 |
| 数据源 | /proc/stat、/proc/meminfo、/proc/diskstats（或 /proc/self/mountinfo + statfs）、/proc/net/dev |
| 实现约束 | 仅用 os.ReadFile 读文本 + 手工解析，不引入 psutil 类依赖（保持零第三方依赖）；CPU 百分比用两次采样差值/总时间差计算 |
| 配置 | `collect.resource_interval_seconds`（默认 5，固定值，防误改，R-03） |

```go
type ResourceSample struct {
    TS          int64   // Unix 秒
    CPUPercent  float64 // 0-100
    MemUsedMB   float64
    MemPercent  float64
    DiskUsedMB  float64
    DiskPercent float64
    NetRxBps    uint64  // 自上次采样差值，按间隔折算
    NetTxBps    uint64
}
func RunResourceCollector(ctx context.Context, interval time.Duration, sink chan<- ResourceSample) error
```

错误处理：单次读取失败（如 /proc 文件瞬时不可读）记 `system_events`（source=collector）并跳过本次，不退出协程；连续 10 次失败才升级为 error 并退出（由 supervisor 重启）。

### 3.2 M-02 连接监听模块（conntrack）

| 项 | 定义 |
| :--- | :--- |
| 职责 | 订阅内核 conntrack 事件流，产出全量连接记录 |
| 数据源 | netlink 组播（NFNLGRP_CONNTRACK_NEW/UPDATE/DESTROY）；Go 侧用 `github.com/florianl/go-conntrack`（netlink 层依赖，全量依赖清单见 3.2.2）或自实现 netlink 解析（实施时二选一，见 3.2.2） |
| 关键参数 | NetlinkBufferSize = 2MB（默认 100KB 调大，R-10）；开启 nf_conntrack_acct（默认开，取每流包/字节数）。**内核侧启用动作**（应用侧配置之外）：部署脚本执行 `sysctl net.netfilter.nf_conntrack_acct=1`（或写入 /etc/sysctl.d/99-sentry.conf + 加载时 modprobe 参数），并回读确认；sysctl 路径不可用时记 system_event warn（包/字节字段为 0，不影响事件记录） |
| 配置 | `conntrack.buffer_size_kb`（默认 2048）、`conntrack.enable_acct`（默认 true）、`conntrack.overrun_warn_interval_s`（默认 60） |

```go
type ConnEvent struct {
    TS      int64
    EvType  int    // 1=NEW 2=UPDATE 3=DESTROY（按 conntrack 事件类型映射）
    Proto   uint8  // 6=TCP 17=UDP 1=ICMP
    SrcIP   uint32 // IPv4 无符号 32 位
    SrcPort uint16 // ICMP 时为 0
    DstIP   uint32
    DstPort uint16
    Packets uint64 // acct 开启时有值，否则 0
    Bytes   uint64
    Mark    uint32 // 防火墙 mark，用于识别被标记的连接
}
func RunConntrackListener(ctx context.Context, cfg ConntrackCfg, sink chan<- ConnEvent, overrun chan<- OverrunInfo) error
type OverrunInfo struct{ TS int64; Dropped uint64 }
```

**3.2.1 溢出监控（R-10 落地）**：netlink 提供溢出计数（NLMSG_ERROR / 内核统计），每 60s 检查一次计数差值；发现溢出时：写入 `system_events`（source=conntrack, level=warn，含丢弃数），并尝试动态扩容缓冲（上限 8MB）；扩容失败维持现状并持续告警。溢出痕迹永留存，符合"只记录"精神（记录"丢了什么"也是记录）。

**3.2.2 实施选型约束**：优先使用 `github.com/florianl/go-conntrack`（成熟、支持事件订阅与 netlink 缓冲配置）；若该库在目标内核版本上出现兼容问题，回退自实现 netlink 解析（cmsg 解析 ctnetlink 消息），两者接口一致（上述 `RunConntrackListener` 签名），M1 内部决策，不改变外部接口。**第三方依赖全清单**（全文共四处依赖，禁止新增）：go-conntrack（netlink 层）、journal 解析库（纯 Go journal 文件解析，参考 Velocidex/go-journalctl 实现思路，见 3.3）、websocket 库（3.7 二选一）、golang.org/x/sys（statfs 磁盘水位，7.3）；其余自身逻辑零依赖。

**3.2.3 ss 快照子职责（connSnapshotter，展示通道）**：正常模式下每 `ss.snapshot_interval_s`（默认 20s）执行 `ss -tanup` 并解析为当前连接列表，仅供面板"当前连接列表"与"活跃连接数"（3.7）使用，**不落库**（全量记录由 conntrack 通道承担）。快照会漏短连接（已知，SEA-001），由 conntrack 全量记录补偿。conntrack 不可用时的降级模式见 3.2.4。

```go
type ConnSnapshot struct {
    TS   int64
    Conn []SnapConn // 当前活动连接（TCP/ UDP）
}
type SnapConn struct {
    Proto   uint8
    SrcIP   uint32
    SrcPort uint16
    DstIP   uint32
    DstPort uint16
    State   string // LISTEN/ESTABLISHED/TIME_WAIT/...
    Pid     int    // 本机进程（可空）
}
func RunConnSnapshotter(ctx context.Context, interval time.Duration, latest *atomic.Value /* *ConnSnapshot */) error
```

**3.2.4 可用性探测与降级**：nf_conntrack 模块由内核依赖链自动加载（无需 modprobe）；**不以 `/proc/net/nf_conntrack` 存在性判定模块可用性**（该文件缺失可能是 CONFIG_NF_CONNTRACK_PROCFS not set 内核编译配置，DEV-032 现场确认非故障），可用性由 netlink Open/Register 直接探测；连续 3 次启动失败（如容器缺 NET_ADMIN）按 R-07 分支：记录 system_event 并降级为 ss 快照 diff 近似事件（每 5s 快照对比变化近似 NEW/DESTROY，明确标注为近似通道），不阻塞启动。

| 连接治理 | 每连接读写超时 30s；全局并发上限 200（超出立即断开）；每源 IP 限速 10 连接/分钟（固定窗口，超限立即断开）——防 DoS 与资源耗尽；统计累计连接数/活跃数/读写字节数/拒绝数（`Server.Stats()`） |
| 事件流 | 新事件类型 `event.CredEvent{TS, Proto, SrcIP uint32, Username, Password, Extra}`，经 `event.Channels.Cred` 通道（有界 4096，非阻塞投递）→ store 单写线程批量落 `cred_events` 表；system_events 只记录连接/IP/协议（限频 1/分钟），**凭据内容禁止写入日志**（红线） |
| 凭据语义 | 明文协议（telnet/ftp/redis/postgres）捕获明文密码；加密/哈希协议（mysql/mongodb/mssql/smb）仅捕获不可逆摘要（Extra 注明 hash 类型）；rdp（TLS 加密）与 memcached（协议无认证）**诚实降级**：记录连接尝试 + Extra 注明限制 |
| 安全红线 | 不执行任何命令；不回传真实系统信息（响应全部为伪造最小握手/拒绝报文）；凭据明文存本地 SQLite（本地单机工具定位，任务书裁定）；前端默认遮蔽密码展示（点击显示） |
| 配置 | `honeypot.enabled`（默认 false 保守，部署时显式启用）、`honeypot.listen`（10 协议映射） |

**协议实现对照表**（字节级实现以 RFC/协议规范为准，手写最小实现，零新依赖）：

| 协议 | 握手要点 | 可捕获凭据 | 限制/说明 |
| :--- | :--- | :--- | :--- |
| telnet（23） | banner → login:/Password: 循环（每 IP 限 5 轮）→ Login incorrect | 用户名+密码（明文） | 不实现 IAC 选项协商（0xFF 按行数据丢弃） |
| ftp（21） | 220 → USER→331 → PASS→530（支持重试多组）→ QUIT | 用户名+密码（明文） | 其他命令回 502 最小响应 |
| redis（6379） | RESP 数组解析；AUTH <pass> / AUTH <user> <pass>；HELLO 3 AUTH | 用户名（可空）+密码（明文） | 兼容 inline 命令行；非 AUTH 命令回 -ERR |
| postgres（5432） | StartupMessage（user 明文）→ R(3) 诱导明文密码 → p 消息 → E 拒绝 | 用户名+密码（明文） | 协议版本仅支持 3.0（196608） |
| mysql（3306） | HandshakeV10（salt 20B）→ HandshakeResponse41 → ERR 1045 | 用户名明文 + auth-response hex | mysql_native_password SHA1 链不可逆（extra 注明） |
| mongodb（27017） | OP_QUERY/OP_MSG → saslStart/saslContinue → payload.user | 用户名明文 + client nonce | SCRAM-SHA-1/256 盐化哈希不可逆（extra 注明） |
| mssql（1433） | Prelogin → 回 Prelogin Response → LOGIN7 → ERROR 18456 | 用户名明文 + TDS 密码字段 hex | TDS 混淆字段（XOR 0xA5+逆序）按任务书仅记录摘要不还原 |
| smb（445） | SMB2 Negotiate（challenge 8B）→ Session Setup（NTLMSSP AUTH）→ STATUS_LOGON_FAILURE | Domain\User 明文 + NTLMv2 Response hex | NTLMv2 哈希不可逆（extra 注明） |
| rdp（3389） | X.224 CR（cookie）→ Connection Confirm → 断开 | 无（cookie/mstshash pre-auth 线索入 extra） | TLS 通道凭据加密无法解析——诚实降级 |
| memcached（11211） | 文本协议首命令解析 → ERROR | 无 | 协议无认证机制——如实记录命令概览 |

- `setup_firewall.sh` 增蜜罐端口放行段（SENTRY_HONEYPOT：INPUT 链 ACCEPT 插入于 DROP 前；raw PREROUTING 入站 LOG 不受影响——蜜罐流量继续进入防火墙事件；配置驱动读 config.json 的 honeypot.listen，未启用时保持原 DROP 行为；--rollback 覆盖删除）；

## 4. SQLite 数据模型

### 4.1 设计要点

1. **存储格式**：IPv4 统一存 INTEGER（无符号 32 位），由应用层转换：`IP→uint32`（`binary.BigEndian.Uint32(net.IP.To4())`），显示时反向转换。理由：4 字节 vs TEXT 15 字节，在"被扫描/攻击月数十 GB"量级下节省 2–4 倍存储与索引空间；代价是原始可读性差，由 API 层统一转换，SQL 查询示例见 4.4。
2. **IPv6**：存 TEXT（最长 45 字符）；VPS 场景 IPv6 连接占比低，不做二进制优化。
3. **时间戳**：全部 int64 Unix 秒。面板时间粒度（秒）足够；不需要毫秒级。
4. **不做数据预过滤**：所有采集行原样入库；字段默认值补全（如端口为 0、用户为空串），不允许因字段缺失丢行。
5. **写入频率评估**：资源 5s/行（17280 行/天）；连接事件常态 0.1–10/s（0.9–86 万行/天），扫描期 10–100/s（86–864 万行/天）；SSH 尝试常态 <0.1/s，暴力破解期 <20/s；防火墙事件受内核限速（默认 5/s 突发 10），上界约 43–86 万行/天。

### 4.2 DDL 草案（M2 按此实施）

```sql
-- 建库初始化执行一次（含 PRAGMA）
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
PRAGMA foreign_keys = ON;

-- 资源采样：5s 一行
CREATE TABLE IF NOT EXISTS resources (
    id           INTEGER PRIMARY KEY,
    ts           INTEGER NOT NULL,          -- unix 秒
    cpu_percent  REAL    NOT NULL,          -- 0-100
    mem_used_mb  REAL    NOT NULL,
    mem_percent  REAL    NOT NULL,
    disk_used_mb REAL    NOT NULL,
    disk_percent REAL    NOT NULL,
    net_rx_bps   INTEGER NOT NULL DEFAULT 0,
    net_tx_bps   INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_resources_ts ON resources(ts);

-- 连接事件：conntrack 全量
-- 注（M2 补充）：src_ip6/dst_ip6 为 IPv6 文本列（方案 4.1"IPv6 存 TEXT"落地），
-- IPv4 连接时为空串；DDL 在 M2 实施时加入，与 4.1 设计要点一致。
CREATE TABLE IF NOT EXISTS connections (
    id       INTEGER PRIMARY KEY,
    ts       INTEGER NOT NULL,
    ev_type  INTEGER NOT NULL,              -- 1=NEW 2=UPDATE 3=DESTROY
    proto    INTEGER NOT NULL,              -- 6=TCP 17=UDP 1=ICMP
    src_ip   INTEGER NOT NULL,              -- IPv4 无符号 32 位
    src_port INTEGER NOT NULL,
    dst_ip   INTEGER NOT NULL,
    dst_port INTEGER NOT NULL,
    packets  INTEGER NOT NULL DEFAULT 0,
    bytes    INTEGER NOT NULL DEFAULT 0,
    mark     INTEGER NOT NULL DEFAULT 0,
    src_ip6  TEXT    NOT NULL DEFAULT '',
    dst_ip6  TEXT    NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_conn_ts    ON connections(ts);
CREATE INDEX IF NOT EXISTS idx_conn_dport ON connections(dst_port);
CREATE INDEX IF NOT EXISTS idx_conn_src   ON connections(src_ip);

-- SSH 登录尝试
CREATE TABLE IF NOT EXISTS ssh_attempts (
    id          INTEGER PRIMARY KEY,
    ts          INTEGER NOT NULL,
    src_ip      INTEGER NOT NULL,
    username    TEXT    NOT NULL DEFAULT '',
    auth_method TEXT    NOT NULL DEFAULT '',
    result      INTEGER NOT NULL,           -- 1=成功 0=失败 2=未知
    fingerprint TEXT    NOT NULL DEFAULT '',
    detail      TEXT    NOT NULL DEFAULT '' -- 原始行截断 512 字符
);
CREATE INDEX IF NOT EXISTS idx_ssh_ts   ON ssh_attempts(ts);
CREATE INDEX IF NOT EXISTS idx_ssh_src  ON ssh_attempts(src_ip);
CREATE INDEX IF NOT EXISTS idx_ssh_user ON ssh_attempts(username);

-- 防火墙事件（采样视图）
CREATE TABLE IF NOT EXISTS firewall_events (
    id       INTEGER PRIMARY KEY,
    ts       INTEGER NOT NULL,
    chain    TEXT    NOT NULL,              -- input/forward
    action   TEXT    NOT NULL,              -- drop/reject
    proto    INTEGER NOT NULL,
    src_ip   INTEGER NOT NULL,
    src_port INTEGER NOT NULL,
    dst_ip   INTEGER NOT NULL,
    dst_port INTEGER NOT NULL,
    raw      TEXT    NOT NULL DEFAULT ''    -- 原始内核日志行
);
CREATE INDEX IF NOT EXISTS idx_fw_ts     ON firewall_events(ts);
CREATE INDEX IF NOT EXISTS idx_fw_dport  ON firewall_events(dst_port);
CREATE INDEX IF NOT EXISTS idx_fw_action ON firewall_events(action);

-- fail2ban 封禁事件
CREATE TABLE IF NOT EXISTS ban_events (
    id   INTEGER PRIMARY KEY,
    ts   INTEGER NOT NULL,
    ip   INTEGER NOT NULL,
    type TEXT    NOT NULL,                  -- ban/unban/found
    jail TEXT    NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_ban_ts ON ban_events(ts);
CREATE INDEX IF NOT EXISTS idx_ban_ip ON ban_events(ip);

-- 采集器自身事件（溢出、降级、告警、归档记录）
CREATE TABLE IF NOT EXISTS system_events (
    id      INTEGER PRIMARY KEY,
    ts      INTEGER NOT NULL,
    source  TEXT    NOT NULL,               -- collector/conntrack/ssh/fw/f2b/archiver/disk/honeypot
    level   TEXT    NOT NULL,               -- info/warn/error
    message TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_se_ts ON system_events(ts);

-- DEV-HONEY-001：蜜罐凭据捕获（M-B）
-- 敏感信息：明文协议（telnet/ftp/redis/postgres）为攻击者提交的明文密码；
-- 加密/哈希协议（mysql/mongodb/mssql/smb）为不可逆摘要（extra 注明 hash 类型）；
-- rdp/memcached 无认证捕获能力（extra 注明限制）。凭据仅本地存储，禁止导出/外传。
CREATE TABLE IF NOT EXISTS cred_events (
    id       INTEGER PRIMARY KEY,
    ts       INTEGER NOT NULL,
    proto    TEXT    NOT NULL,              -- mysql/redis/memcached/mssql/mongodb/postgres/rdp/smb/telnet/ftp
    src_ip   INTEGER NOT NULL,              -- IPv4 无符号 32 位（IPv6 记 0，字段限制）
    username TEXT    NOT NULL DEFAULT '',
    password TEXT    NOT NULL DEFAULT '',
    extra    TEXT    NOT NULL DEFAULT ''
);
CREATE INDEX IF NOT EXISTS idx_cred_ts    ON cred_events(ts);
CREATE INDEX IF NOT EXISTS idx_cred_src   ON cred_events(src_ip);
CREATE INDEX IF NOT EXISTS idx_cred_proto ON cred_events(proto);

-- 元信息
CREATE TABLE IF NOT EXISTS meta (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
-- 预置项：schema_version=1, created_at, hostname, os_release, kernel
```

### 4.3 索引设计说明

| 索引 | 服务查询 | 代价评估 |
| :--- | :--- | :--- |
| *_ts（全部表） | 时间范围查询、归档导出（WHERE ts BETWEEN） | 追加型写入，B-tree 顺序插入代价低 |
| idx_conn_dport | 攻击端口 TOP（GROUP BY dst_port WHERE ts 范围） | 攻击热点端口少量，选择性高 |
| idx_conn_src | 攻击源 IP TOP | 同上 |
| idx_ssh_src / idx_ssh_user | 暴力破解源与账号统计 | SSH 行数相对少 |
| idx_fw_dport / idx_fw_action | 被攻击端口统计（限速后行数有上界） | 行数受限速约束 |
| idx_ban_ts / idx_ban_ip | 封禁时间线 | 行数极少 |

索引取舍原则：仅建查询实际用到的索引；不建 `(ts, dst_port)` 复合索引（ts 单列预期选择性已足够；此项为**预留优化项**：M2 压测时若 GROUP BY 查询超 100ms，再补复合索引并回写本表）。

### 4.4 关键查询 SQL 草案（API 层使用）

```sql
-- 攻击端口 TOP（防火墙采样视图，面板主图）
SELECT dst_port, COUNT(*) AS hits
FROM firewall_events
WHERE ts >= ?1 AND action = 'drop'
GROUP BY dst_port ORDER BY hits DESC LIMIT ?2;

-- 攻击源 IP TOP
SELECT src_ip, COUNT(*) AS hits FROM firewall_events
WHERE ts >= ?1 GROUP BY src_ip ORDER BY hits DESC LIMIT ?2;

-- 活跃连接数：不使用 SQL 计算。原因：NEW−DESTROY 窗口差值会系统性漏计
-- 存活超过窗口的长连接（SSH 会话、数据库连接等无事件静默期）。
-- 正确口径：connSnapshotter 最新 ss 快照的连接计数（见 3.7 说明）。

-- SSH 失败时间线（每小时聚合）
SELECT ts/3600 AS hour, COUNT(*) AS fails FROM ssh_attempts
WHERE ts>=?1 AND result=0 GROUP BY hour;

-- 归档副本生成（archiver 使用，D-04 永久保留：只导出不删除主库）
ATTACH 'archive/2026-07.db' AS arc;
INSERT INTO arc.connections SELECT * FROM main.connections WHERE ts BETWEEN ?1 AND ?2;
-- ... 各表同理（resources/ssh_attempts/firewall_events/ban_events）
-- 主库数据保留不动（无 DELETE）；归档文件随后 gzip 压缩
```

### 4.5 写入路径与容量论证

- **单写线程**：WAL 模式单写者限制由唯一写协程化解（SEA-001）；所有 INSERT/DELETE/ATTACH 均在该协程内串行执行。
- **批量事务**：每 1s 或积满 500 行提交一次；`BEGIN IMMEDIATE` 防止归档作业交叉（同一写线程内本无竞争，IMMEDIATE 为防御性）。
- **事件率上界论证**：1C1G 上 SYN flood 时连接事件率受 nf_conntrack_max（默认 65536）与 SYN 超时（约 60s）共同约束，理论上限约 1092/s；实际单核收包 + conntrack 查表处理能力通常低于此（数百/s 量级），实际难达理论上限。**容量推导公式**：日事件数 = 事件率 × 86400；行均大小假设约 150B（数据行 ~60–80B + 索引与 WAL 摊销 ~70–90B，M4 实测校准）。按此：500/s → 4320 万行/天 → 约 6.5GB/天；1000/s（理论上限）→ 约 13GB/天。千行批量插入目标 <50ms/批（V3 验证），写路径余量 ≥20 倍；攻击期 CPU 超标属既定取舍（第 5 章）。
- **WAL 文件大小**：默认 checkpoint 阈值 1000 页（约 4MB）；写入高峰 WAL 临时膨胀至数十 MB 属正常，checkpoint 后回落；磁盘预算按主库 + WAL（预留 200MB 峰值）计算。

### 4.6 保留策略与归档（D-04 定稿：永久保留）

| 项 | 策略 | 说明 |
| :--- | :--- | :--- |
| 主库保留 | **数据永久保留、永不删除**（D-04） | 无保留期、无滚动删除；任何时点任意 range 查询均落在主库内，不缺档 |
| 归档 | **仅压缩副本，不删除**：超过 `archive.copy_after_days`（默认 60 天）的数据按所属自然月导出为独立 SQLite 文件并 gzip，主库原数据不动 | 副本 = 灾备/离线回溯/未来迁移载体；磁盘按"主库全量 + 压缩副本"规划（7.2） |
| WAL 维护 | 定期 checkpoint（wal_autocheckpoint 默认 1000 页）+ 每季度一次全量快照（VACUUM INTO，可选） | 主库纯追加（无 DELETE），碎片可控；VACUUM INTO 仅作快照备份手段，不回收空间 |
| 启动自愈 | 启动时发现 `.tmp` 归档文件 → 续跑上次归档；meta 表记录已归档月份 | 崩溃恢复路径 |
| 查询边界与性能 | 主库在线查询覆盖全部历史（range 任意，默认 24h/7d/30d）；查询均按 ts 范围过滤，B-tree 索引范围扫描复杂度与"范围行数"成正比，**面板默认范围性能不随历史总量增长**；深层历史查询（如一年前整月）扫描行数多，属用户主动选择，可接受 | 永久保留 = 全量在线 + 压缩副本备份；归档副本不提供在线查询（解压 + sqlite3 离线回溯） |

## 5. 资源预算与目标对照

### 5.1 预算口径（引自 SEA-001，标注证据状态）

**采集端口径（sentry-agent 自身，不含 fail2ban）**

| 指标 | 预算值 | 状态 | 依据 |
| :--- | :--- | :--- | :--- |
| 常驻内存 | 15–70MB | 达标（<100MB） | Go 基准 10–50MB + conntrack 缓冲/队列余量（估算） |
| 常驻 CPU | 典型 0.6–1.5%，峰值上界 2.6% | 达标（<1%~2% 边界内） | 事件驱动 + 5s 轮询（估算，V2 压测验证） |

**全栈口径（含 fail2ban，实测 63MB）**

| 指标 | 预算值 | 状态 | 依据 |
| :--- | :--- | :--- | :--- |
| 常驻内存 | 78–133MB | 下界达标，上界超标 | fail2ban 63MB 为实测；结果取决于 fail2ban 版本与 jail 数 |
| 常驻 CPU | 典型 1.6–2.5%，峰值上界 3.6% | 上界超标 | fail2ban 轮询 + 采集叠加 |

**结论**：采集端（核心承诺）达标；全栈口径下界达标、上界超标——用户决策 D-02 已定稿**保留 fail2ban**（第 10 章），全栈上界超标作为已接受的取舍记录。

**容器运行开销说明（D-01 定稿后新增口径）**：

| 项 | 说明 |
| :--- | :--- |
| Docker 运行时开销 | Docker 守护进程（dockerd）本身是宿主既有组件，不计入 sentry-agent 预算；容器仅承担进程隔离（namespace/cgroup），Go 二进制在容器内运行开销与裸机一致（无解释器、无额外运行时）；容器文件系统层（镜像）只占磁盘、不占常驻内存 |
| 预算口径更新 | 采集端预算（15–70MB）为容器内 sentry-agent 进程口径，与裸机口径相同；fail2ban 位于宿主机（D-02），全栈口径（78–133MB）= 容器内进程 + 宿主 fail2ban，核算口径不变 |
| 内核 netlink 缓冲 | 2MB netlink 缓冲分配在进程内存，容器内与裸机一致，不因容器化改变 |

### 5.2 数据量与磁盘估算（估算状态，M4 实测校准）

| 场景 | 事件/日志速率 | 日增量估算 | 月增量估算（30 天） |
| :--- | :--- | :--- | :--- |
| 正常 | 连接 0.1–10/s，防火墙 <0.1/s，SSH <0.1/s | 13–130MB（SEA-001） | 0.4–4GB |
| 被扫描 | 连接 10–100/s，防火墙限速满（5/s 突发 10） | 0.9–8.6GB（SEA-001，含内核日志原始口径） | 27–258GB |
| DDoS | 连接数百–1000/s（受 conntrack 上限约束） | 17+GB（SEA-001，防火墙日志未限速口径） | 数百 GB |

说明：SEA-001 的"被扫描/DDoS"口径是**内核原始日志**（未限速）；本方案防火墙通道限速 5/s 后，防火墙表日增约 43–86 万行（约 150–300MB 含索引与 raw）。连接表容量按 4.5 推导：扫描期 10–100/s → 86–864 万行/天 → 约 0.13–1.3GB/天（行均 150B）；极端 DDoS 500/s → 约 6.5GB/天，理论上限 1000/s → 约 13GB/天（实际受单核处理能力约束，通常达不到；M4 压测校准）。磁盘规划与水位监控见第 7 章；此为估算，M4 压测（V2 扩展）后校准数值。

### 5.3 目标对照表

| 目标 | 目标值 | 采集端预算 | 全栈预算 | 判定 |
| :--- | :--- | :--- | :--- | :--- |

### 6.2 分支处理逻辑（对应 C 项）

| 分支 | 触发条件 | 处理动作 | 影响 |
| :--- | :--- | :--- | :--- |
| A | systemd + journald 持久化（默认主流发行版） | SSH/防火墙均走 journal 挂载通道解析；按 6.5.1 调整 RateLimit | 全功能 |
| B1 | 无 systemd（如 Alpine 默认 openrc） | SSH 走 `tail -F /var/log/auth.log`（rsyslog 或 syslogd 落盘，容器挂载该文件）；防火墙走 /dev/kmsg 读取（需特权挂载） | 功能等价，解析器源切换（R-08 已预案） |
| B2 | journald 存在但非持久 | 部署脚本写 /etc/systemd/journald.conf.d/99-sentry.conf 启用 Storage=persistent 并 restart journald；不可行则走 B1 | 需重启 journald（短暂日志 gap，记录 system_event） |
| B3 | 未知发行版 | 通用安装（Docker + 二进制镜像），采集端不依赖发行版包管理器；仅 fail2ban 安装方式按发行版差异处理（6.5.4） | 仅安装方式差异 |
| B4 | 内核 <3.10 | 警告并继续（conntrack 事件流可能异常）；M1 的 V1 验证在该环境重跑，失败则降级 B5 | 记录告警 |
| B5 | conntrack 通道不可用（容器缺少 --network host/NET_ADMIN、宿主 OpenVZ/模块缺失） | 连接通道降级为 ss 快照 diff 近似事件（5s）；面板标注"近似通道，非全量"；system_event 记录降级原因 | 记录能力降级，DDoS 场景数据不完整（环境限制，符合 R-07 预案） |
| B6 | fail2ban 后端与防火墙后端不一致 | 按 C-07 判定结果重装/切换 fail2ban 后端（iptables↔nftables 规则集不互通，R-06）；拒绝自动切换则禁用 M-05 | 阻塞项：必须人工决策后端对齐，部署脚本打印指引后退出 |
| B7 | 容器 journal 挂载不可读（权限/挂载失败，C-12 未通过且 ACL 修复失败） | 回退挂载 rsyslog 文本文件（auth.log/kern.log，分支 B1 形态）或提示人工修复；system_event 记录 | 能力降级：丢失 journal 结构化字段，内核日志依赖文本文件 |
| B8 | Docker 运行时不可用（C-13 失败） | 提示安装 Docker（6.4 指引）；用户拒绝容器化则回退裸机 systemd 运行方式（6.3 保留的备选路径，功能等价） | 部署方式差异，采集能力不变 |

### 6.3 systemd 服务设计（裸机运行备选，开发与回退路径）

> 用户决策 D-01 定稿：最终交付为 Docker 镜像。本节约定保留的**裸机运行方式**，用于开发调试、CI 测试与 Docker 不可用（分支 B8）时的回退；功能与容器形态完全等价。

```ini
# /etc/systemd/system/sentry-agent.service
[Unit]
Description=Sentry Agent - lightweight security posture collector
After=network.target systemd-journald.service
Wants=network.target

[Service]
Type=simple
User=sentry
Group=sentry
ExecStart=/usr/local/bin/sentry-agent --config /etc/sentry-agent/config.json
Restart=on-failure
RestartSec=5
# 加固（8.1）：禁止提权与写系统区
NoNewPrivileges=yes
ProtectSystem=strict
ReadWritePaths=/var/lib/sentry-agent
PrivateTmp=yes
ProtectHome=yes
ProtectKernelTunables=yes
ProtectControlGroups=yes
# 读取 journald 需要（journalctl -f 需访问 /var/log/journal 与 systemd 通讯）
# 若实测权限不足，追加：SupplementaryGroups=systemd-journal
[Install]
WantedBy=multi-user.target
```

> 权限注意：`ProtectSystem=strict` 下仅 ReadWritePaths 目录可写；journald 流式读取以专用用户运行时需要 systemd-journal 组读权限（C-12 检查），实施时按实测调整 SupplementaryGroups。conntrack netlink 组播读取通常不要求特权（M1 实测确认项）。**特权取舍披露**：若 M1 实测确认需特权，将评估两个方案并记录结论——①维持专用用户 + `AmbientCapabilities=CAP_NET_ADMIN`（最小化 capability 集合，但仍与 8.1"不持有修改防火墙权限"的声明存在张力，届时需更新 8.1 声明）；②root 运行 + 其余 capability 全部 drop（更简单但权限更大）。默认目标为无特权读取，方案按此设计；最终取舍在 M1 结论中记录并同步修订 8.1。

### 6.4 Docker 部署设计（D-01 定稿：最终交付形态）

**6.4.1 多阶段构建 Dockerfile 草案（M4 交付物，此处为设计草案）**

```dockerfile
# ===== builder 阶段 =====
FROM golang:1.24-alpine AS builder        # Go 版本以 M1 实施时 go.mod 锁定为准
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/sentry-agent ./cmd/sentry-agent

# ===== 运行时阶段 =====
# 基础层定稿（DEV-008，M4 实测）：debian:bookworm-slim + systemd（journalctl）+ iproute2（ss）。
# 演进记录：最初选 alpine（~3MB），实测发现两处硬缺口——①alpine 无 systemd 包（journalctl 不可用），
# 而默认配置 ssh.source=journald / fw.source=journald-kernel 依赖 journalctl 二进制；
# ②busybox-extras 不含 ss（B5 降级/snapshot 依赖）。debian-slim + systemd + iproute2 补齐两者。
# 后续若实现纯 Go journal 解析器（V1b-2 复验项）可移除 systemd 依赖、评估切回 slim/scratch。
# 镜像大小目标：压缩后 <50MB。
# 实测（DEV-008，2026-08-14，debian 定稿版）：解压后 177MB、docker save + gzip 压缩后 42.65MB —— 达标。
FROM debian:bookworm-slim
RUN apt-get update -qq \
    && apt-get install -y -qq --no-install-recommends systemd iproute2 ca-certificates tzdata \
    && rm -rf /var/lib/apt/lists/* \
    && useradd -r -u 1000 -m -d /home/sentry -s /usr/sbin/nologin sentry
COPY --from=builder /out/sentry-agent /usr/local/bin/sentry-agent
USER sentry
EXPOSE 8080
ENTRYPOINT ["/usr/local/bin/sentry-agent", "-config", "/etc/sentry-agent/config.json"]
# 配置：/etc/sentry-agent/config.json（只读挂载）；数据：/var/lib/sentry-agent（卷挂载，rw）
# 容器内 journal 读取：挂载 /var/log/journal:/var/log/journal:ro（代码默认路径，6.4.3 挂载表）
# 容器内 ss：iproute2 提供（B5 降级依赖）
```

**6.4.2 运行方式与网络模式（结论：`--network host` 为必要配置）**

| 项 | 结论 | 依据（searcher 调研） |
| :--- | :--- | :--- |
| 网络模式 | **必须 `--network host`**（与宿主共享网络命名空间） | conntrack 是网络命名空间（netns）级状态：默认 bridge 模式下容器位于自己的 netns，ctnetlink 只能订阅容器自身连接（且 bridge 容器 netns 内 conntrack 通常未激活）；host 模式下可订阅宿主全部连接事件（netlink(7)、Docker 官方文档，把握度高） |
| 所需 capability | **`--cap-add=NET_ADMIN`**（NET_RAW 不足） | Docker 默认 capability 集不含 NET_ADMIN（moby oci/caps/defaults.go，官方默认保留 14 项）；netlink(7) 规定订阅组播组需 UID 0 或 CAP_NET_ADMIN；root 豁免在 Docker 场景未实测（推断），配置一律显式携带 cap（把握度高，root 豁免细节待 M1 实测） |
| 端口映射 | `--network host` 下 `-p` 失效；Web 面板直接 bind 监听地址 | `web.listen` 默认 127.0.0.1:8080（宿主回环，仅本机）；用户可改 0.0.0.0（D-03，暴露面自担） |
| 无关项 | `--pid host` 对 conntrack -E 无影响；无需挂载宿主 /proc | searcher 调研（把握度中高） |
| 镜像内进程视角 | 容器内 /proc 为容器自身视图（资源采样读容器内 /proc：CPU/内存近似宿主可用视图；cgroup 限流下内存数值反映容器限制，宿主整机内存需经 /proc/meminfo 宿主视图或宿主导出——**M1 实测确定资源采集口径**：优先容器内 /proc（cgroup 视角），若用户需要宿主全貌则在部署文档说明差异） | 推断，M1 验证 |

```bash
# 运行示例（docker run；compose 等价配置见 6.4.3 后）
docker run -d --name sentry-agent \
  --restart=unless-stopped \
  --network host \
  --cap-add=NET_ADMIN \
  --user 1000:1000 \
  --group-add "$(getent group systemd-journal | cut -d: -f3)" \
  -v /var/lib/sentry-agent:/var/lib/sentry-agent \
  -v /var/log/journal:/var/log/journal:ro \
  -v /etc/machine-id:/etc/machine-id:ro \
  -v /var/log/fail2ban.log:/host/fail2ban.log:ro \
  -v /var/lib/fail2ban/fail2ban.sqlite3:/host/fail2ban.sqlite3:ro \
  -v /etc/sentry-agent/config.json:/etc/sentry-agent/config.json:ro \
  sentry-agent:latest
```

> 备注：`/etc/machine-id` 挂载为 journalctl 备选路径（`-D` 模式）所需；若 M1 实测确认纯 Go 解析器以目录参数直接读取（不依赖 machine-id 解析），可移除该挂载以缩小宿主文件暴露面（M1 验证排期项）。

**6.4.3 卷挂载清单与权限设计**

| 挂载点 | 容器路径 | 读写 | 用途 | 权限要求 |
| :--- | :--- | :--- | :--- | :--- |
| /var/lib/sentry-agent | /var/lib/sentry-agent | rw | SQLite 主库 + 归档副本目录（数据卷，Docker named volume 或 bind mount） | 容器 UID 1000 属主 |
| /var/log/journal | /var/log/journal | ro | SSH 认证日志 + 内核日志（防火墙 LOG）；挂载到容器内代码默认路径（journalctl -f 无 -D 模式，DEV-008 修订，原 /host/journal 设计废弃） | 目录 2755 root:systemd-journal、文件 0640；容器以 `--group-add systemd-journal GID` 读取（默认 dockerd 有效）；**userns-remap/rootless Docker 下 GID 映射失效 → 备选宿主 ACL**：`setfacl -Rnm u:1000:rx,d:u:1000:rx /var/log/journal/`（容器 UID 1000，含默认 ACL 保证轮转新文件权限，DEV-008 修订） |
| /etc/machine-id | /etc/machine-id | ro | journalctl 默认路径读取的 machine-id 匹配（-D 模式未实现，已废弃）；纯 Go 解析器就绪后可移除 | 0644 只读 |
| /var/log/fail2ban.log | /host/fail2ban.log | ro | M-05 fail2ban 事件 | 0640 root:adm（Debian）或 root:root（RHEL）；容器 UID 1000 不可读 → 部署脚本调整 ACL 或 chmod g+r（宿主侧一次性操作，属 fail2ban 安装清单 6.5.4 一部分） |
| /var/lib/fail2ban/fail2ban.sqlite3 | /host/fail2ban.sqlite3 | ro | M-05 封禁名单查询（每 60s） | 同上，只读 ACL |
| /etc/sentry-agent/config.json | /etc/sentry-agent/config.json | ro | 配置文件 | 0640 root:root（无密钥，仅路径参数） |

> 权限原则：容器非 root 运行（UID 1000），仅通过"补充组匹配或宿主 ACL"获得日志只读权限；不 chmod 0644 放宽 journal（含安全敏感日志）。fail2ban 日志/库的读取权限调整在 fail2ban 安装清单中一并完成（6.5.4）。

**6.4.4 容器化技术可行性依据与验证排期**

| 技术点 | 结论 | 证据来源 | 把握度 |
| :--- | :--- | :--- | :--- |
| 容器内 conntrack -E 观察宿主全部连接 | 可行：`--network host`（共享 netns）+ `--cap-add=NET_ADMIN`；bridge 模式不可行（容器独立 netns） | netlink(7) man 页、moby oci/caps/defaults.go（Docker 默认不含 NET_ADMIN）、Docker 官方网络文档（searcher 调研，2026-08） | 高（root 豁免细节待 M1 实测） |

| 镜像大小目标 | 压缩后 <50MB：静态二进制 ~10MB + alpine 基础层 ~3MB；scratch 备选（M4 对比） | 估算（M4 实际构建验证） | 中 |
| 资源采集口径 | 容器内 /proc 为容器视图（cgroup 限流视角）；与裸机口径存在差异 | 推断（M1 实测确定，见 6.4.2 备注） | 中 |

**验证排期（M1）**：
- V1b-1：容器环境 conntrack 验证——`--network host` + `--cap-add=NET_ADMIN` 下启动容器，对比容器内 `conntrack -E` 事件与宿主侧 `conntrack -S`/`ss` 一致性；同时实测"root 不携带 cap-add"时事件订阅是否可用（M1 记录，决定 6.4.2 备注是否需要简化）。
- V1b-2：journal 挂载验证——纯 Go 解析器（或 journalctl -D）读取挂载目录，确认 machine-id 处理方式与 inotify 跟随；实测 `--group-add` 与 ACL 两条权限路径。
- V1b-3：资源采集口径实测——容器内 /proc 读数与宿主读数差异记录，确定 M-01 的最终口径（容器视图 or 需宿主视图）。

**6.5.3 防火墙日志规则（D-05 定稿：仅模式 B，零策略变更）**

> 模式 A（默认拒绝 + 日志化，含其记录边界披露与决策项 D-05 选项①）**已由用户否决（D-05 定稿为模式 B）**，正文不再保留；仅记录本备注以防未来重提。部署脚本只实现模式 B。

**模式 B（定稿）：在现有 DROP 规则前插入限速 LOG，不改变包流向**。fail2ban 的 ban 规则同属"现有 DROP 规则"范畴，模式 B 覆盖（C-07b 盘点其位置）。

```bash
# nftables 分支（C-07 判定后选择）：
# 在 C-07b 盘点出的每条 drop/reject 规则之前插入日志规则（同表同链）：
nft insert rule inet <表> <链> log prefix "SENTRY_FW:input:drop " limit rate 5/second burst 10 packets flags all counter
# 注意：insert 插到链首，多条规则需按 C-07b 清单逐个定位插入位置（部署脚本用 handle 定位，
# 支持 nft -a 显示 handle 后按 handle 添加）；insert 到目标 drop 规则之前的语义为"记录即将被丢弃的包"。

# iptables-legacy 分支：
# 在目标 DROP 规则之前插入：
iptables -I INPUT <规则号> -m limit --limit 5/s --limit-burst 10 -j LOG --log-prefix "SENTRY_FW:input:drop "
# 规则号由部署脚本按 C-07b 盘点结果计算（fail2ban ban 规则插入位置之前）
```

> 要点：①LOG 目标/规则仅记录不拦截，包流向不变（零策略变更，D-05 承诺）；②限速 5/s 突发 10 使该通道事件率有上界（采样性质，面板标注，R-09 首要缓解）；③前缀固定 `SENTRY_FW:`（M-04 仅解析此前缀）；④规则持久化：nftables 写入 /etc/nftables.d/sentry.nft（nft list 导出或脚本生成），iptables 用发行版持久化机制（iptables-persistent 或 firewalld direct）；fail2ban 后端必须与 C-07 判定一致（B6）。M4 以 `nft -c` 语法检查与 `iptables -S` 回读验证。`forward` 链仅在 VPS 承担转发时启用（默认跳过）。

> 适用前提：C-08 检查发现 fail2ban 未安装（空 VPS 场景）。步骤按序执行，每一步有回读校验；部署脚本在 M4 交付。

## 7. "只记录"原则落地设计

### 7.1 对抗系统默认清理机制（R-12 落地）

"只记录"与磁盘有限是根本张力：系统默认的 logrotate、journald SystemMaxUse、auditd num_logs 都会**删除**旧数据，必须显式改为"归档不删除"。

| 组件 | 默认行为 | 本方案配置 | 落地文件 |
| :--- | :--- | :--- | :--- |
| journald | SystemMaxUse 默认 10% 磁盘，满则删旧 | SystemMaxUse=4G + Compress=yes（6.5.1） | /etc/systemd/journald.conf.d/99-sentry.conf |
| logrotate | 轮转后保留 count 份旧档，超出删除 | 自定义配置：`rotate 9999`（保留大量历史档，实际保留量受磁盘水位监控约束，7.3）+ compress + dateext；不采用 `rotate 0`（该值语义为"轮转后立即删除旧档"，与"不删除"意图相反） | /etc/logrotate.d/sentry-archive |
| fail2ban 日志 | 自身日志轮转 | 同 logrotate 策略；fail2ban.sqlite3 只读不删 | 同上 |
| auditd | num_logs 默认 5 份删旧 | 本方案不依赖 auditd（SSH 走 journald/auth.log），若发行版默认开启 auditd，部署脚本不修改其行为，仅确保不使用 auditd 作为数据源（减少一份清理冲突面） | — |
| SQLite 主库 | 无内置清理 | **永久保留、永不删除**（D-04）；旧数据仅生成压缩副本（4.6、3.9），主库无任何删除动作 | sentry-agent 内部 |

**logrotate 配置模板（sentry 相关日志）**

```
/var/log/fail2ban.log {
    daily
    rotate 9999
    compress
    dateext
    missingok
    notifempty
}
```

> 语义说明：logrotate 的 `rotate count` 指"轮转 count 次后删除旧档"，**`rotate 0` 实际语义是"每次轮转后立即删除旧档"**（不保留历史），与"归档不删除"意图相反，故本方案使用 `rotate 9999`（实际保留量受磁盘水位监控约束，7.3；档位规划见 7.2）。历史轮转档的最终清理仅允许人工按磁盘预算手动执行，sentry-agent 与 logrotate 均不自动删除。本方案的核心数据主体是 SQLite 主库（永久保留）+ 压缩副本（仅压缩不删除，D-04），系统日志轮转档为次要数据源。

### 7.2 磁盘容量规划（D-04 定稿：永久保留口径重估）

**增量估算（估算状态，M4 实测校准；口径同 5.2）**

| 组成 | 正常月增量 | 攻击月增量（估算） | 说明 |
| :--- | :--- | :--- | :--- |
| SQLite 主库（全量永久保留） | 0.4–4GB/月 → 年 5–50GB | 扫描 27–258GB/月；极端 DDoS 约 195–390GB/月（4.5 推导 6.5–13GB/天 × 30 天） | 无删除，按月线性累计；DDoS 档为理论上限，实际受单核处理能力约束 |
| 压缩副本（60 天后生成，gzip） | 0.4–4GB/月 → 压缩后 0.1–1GB/月 | 扫描 9–80GB/月（压缩后）；DDoS 档按实际增量推算 | 副本与主库并存（仅压缩不删除，D-04） |
| journald + 系统日志 | ≤4GB（SystemMaxUse 硬上限） | ≤4GB | 上限保护，满时压缩保留 |
| WAL + 临时 | ≤200MB | ≤500MB | checkpoint 后回落 |

**磁盘档位建议（部署前按此选择，C-09 校验）**

| 档位 | 适用场景 | 磁盘建议 | 可支撑容量 |
| :--- | :--- | :--- | :--- |
| 档位 1（默认） | 正常运营（无持续攻击） | ≥80GB | 主库全量 1 年（≤50GB，按正常月上限 4GB/月）+ 副本 gzip 后 1 年（≤12GB）+ 系统日志（≤4GB）+ WAL 与余量（≥10GB），合计约 76GB，取 80GB |
| 档位 2 | 有周期性扫描/攻击 | ≥150GB | 主库全量 6 个月含扫描期（按扫描月占比 ≤1/3 估算）+ 副本 + 系统日志 + 余量 |
| 档位 3 | 频繁攻击（月增量 ≥27GB） | ≥500GB | 主库全量 6 个月含攻击期（按攻击月占比 ≤1/2 估算）+ 副本 + 系统日志 + 余量 |

**容量原则**：永久保留（D-04）下磁盘需求与运行时长、攻击强度线性增长；"只记录"的最终边界是物理磁盘上限（R-09）。缓解组合：防火墙限速（已内置）+ 水位告警（7.3，最高优先级）+ 档位扩容；**不引入任何自动删除行为**。若用户未来磁盘耗尽且不接受扩容，唯一可选项是人工导出后移除最旧压缩副本（副本删除不影响主库全量数据，属可逆操作，在运维文档中说明）。

### 7.3 磁盘水位监控与告警（R-09 最高优先级落地，量化阈值）

> 用户决策 D-04（永久保留）后，磁盘消耗无自动回收机制，**水位监控与告警升级为最高优先级缓解项**：任何静默写满都会导致"只记录"失效（SQLite 写入失败丢数据）。下述阈值为量化默认值，部署文档提供调整指引。

| 阈值 | 动作（量化） |
| :--- | :--- |
| warn：磁盘使用率 ≥80% | system_event（level=warn）+ 面板横幅告警；日志每 10 分钟一次（限频）；面板归档页显示剩余可支撑天数估算（按近 30 天增量速率线性外推） |
| critical：≥90% | system_event（level=error）+ 面板红色横幅；**暂停压缩副本生成**（保留 .tmp 续跑能力，主库写入继续——保记录优先）；每 5 分钟检查 |
| critical：≥95% | 同上 + 运维文档指引人工动作（扩容、或人工移除最旧副本——可逆操作，见 7.2）；sentry-agent 不自动删除任何数据 |

磁盘监控使用 statfs 系统调用（Go 标准库 x/sys 或 syscall），不依赖 df 子进程；监控目标为数据目录所在分区（主库 + 副本目录）。

## 8. 安全设计

### 8.1 最小权限运行（容器形态为主，D-01 定稿）

| 项 | 设计 |
| :--- | :--- |
| 容器用户 | 镜像内非 root 运行（UID 1000，`adduser -D sentry`），无 shell；容器 `--user 1000:1000` |
| capability 最小集 | 仅 `--cap-add=NET_ADMIN`（conntrack 事件订阅必需，searcher 调研结论，见 6.4.4）；不授予 SYS_ADMIN/SYSLOG/NET_RAW 等；`--security-opt no-new-privileges` |
| 特权取舍披露 | NET_ADMIN 属网络管理类能力，host 网络下容器进程理论上具备修改宿主网络配置的能力——这是 conntrack 读取所需的最小可用集（调研结论），缓解面：容器只读挂载（无写权限破坏持久性）、no-new-privileges、镜像无 shell/无额外工具、仅暴露只读 API；风险记录于 R-14 |
| 读取权限 | journal 经 systemd-journal 补充组或宿主 ACL 只读（6.4.3）；fail2ban 日志/库经 ACL 只读（6.5.4）；全部 `:ro` 挂载 |
| 写权限 | 仅数据卷 /var/lib/sentry-agent（属主 UID 1000，目录 0700；state.db 0600） |
| 防火墙规则 | 部署脚本以宿主 root 执行一次（6.5.3）；容器进程不承担规则修改职责（NET_ADMIN 仅为读取 conntrack 之需，见上披露） |
| 配置 | /etc/sentry-agent/config.json 只读挂载（0640 root:root，配置无密钥，仅路径与参数） |
| 裸机运行（备选） | 保留 6.3 systemd 单元加固（NoNewPrivileges、ProtectSystem=strict 等）作为 Docker 不可用时的回退路径，权限项与容器形态等价 |

### 8.2 面板访问安全（D-03 定稿口径）

| 威胁 | 缓解 |
| :--- | :--- |
| 公网暴露 | 默认监听 127.0.0.1（仅回环）；用户修改为 0.0.0.0 时暴露面自担，工具文档给出风险提示（6.7）；面板无写操作接口 |
| 跨站连接本地端口 | WS 升级校验 Origin（web.ws_origin_allow，默认 http://127.0.0.1:8080）；HTTP 接口无写操作（GET 只读 + WS 只收推送），无 CSRF 价值面 |
| 访问边界 | 认证/TLS/隧道等访问控制由用户自配的反代或隧道承担（6.7 参考方式），工具不内置；用户直连 0.0.0.0 时需自行依赖宿主防火墙白名单 |
| 数据泄露 | 数据不出 VPS（本地存储 + 本机监听）；面板无下载/导出敏感原始日志的接口（raw 字段仅 API 按需返回，前端不批量展示） |
| 本地用户 | state.db 0600 + 数据目录 0700（容器 UID 1000），防其他本地用户读取连接/SSH 记录 |

### 8.3 数据本地化与隐私

- 无任何外发通道：不内置上报、无遥测、无云同步；唯一网络出口是 WebSocket 到访问方浏览器的连接（经用户自配的访问通道）。
- 压缩副本与主库文件权限一致（数据目录 0700，文件 0600）。
- 访问链路加密由用户自配方式承担（反代 TLS 或 SSH 隧道，工具不引入证书管理负担）。

## 13. 扩展接口预留说明（非目标）

以下能力明确**不在本轮实施范围**，仅在设计中预留接口位，防止未来扩展时破坏现有架构：

| 扩展方向 | 预留位置 | 说明 |
| :--- | :--- | :--- |
| 多机集中管理 | M-07 API 层抽象（查询协议稳定为 REST + WS）；数据模型含 dst_ip 字段天然支持多机合并 | 未来若集中化：增加"上送"通道（HTTP/HTTPS 推送至中心端），sentry-agent 的采集与存储接口不变；不做中心端设计 |
| 流量包捕获（PCAP） | M-02 事件流旁路点 | 需在连接事件流处增加原始包通道（libpcap 依赖），与轻量化目标冲突，仅注明接入点 |
| eBPF 深度审计 | M-02 数据源抽象层 | 内核版本耦合（R-05），本轮不用；未来可在 conntrack 之外增加 eBPF 事件源，接口签名不变（新增 source 枚举） |
| 告警通知 | system_events 表 + WS 推送帧 | 未来可加通知通道（邮件/webhook），消费端为 system_events 已足够 |
| 聚合/物化表 | 4.4 查询草案预留优化位 | 面板查询量增长后再引入物化聚合，不预建 |
